## 一、 第一性原理与设计背景 (First Principles & Problem Statement)

局域网文件传输的核心目标是**“极简、可靠、无感知地完成端到端数据交换”**。但在当前 EQT 的实际使用场景中，存在两项阻碍用户流畅体验的痛点：

### 1. Receive 模式“单次一锤定音”与会话割裂痛点
- **现状**：当前移动端扫码进入 Receive 接收页后，选择一批文件并完成上传后，界面即进入静态的“传输完成”展示页。
- **痛点**：若用户此时需要追加传输其他照片或文档（例如刚才漏选了某项资料），当前系统无法原地“继续传输”，用户必须强行刷新浏览器网页或重新扫描桌面端二维码建立新的网络连接；更严重的是，之前的传输结果在页面刷新后即刻丢失，缺乏本次会话期间已传文件的上下文追踪（无历史记录）。
- **第一性原理剖析**：HTTP/TCP 连接是短生命周期的，但**“用户跨端传输的会话意图”是长生命周期的**。只要服务端未主动下线，局域网连接和鉴权上下文就应当被复用。系统应当支持在同一会话下流式追加多个传输批次（Multi-Batch Sessions），并为用户提供确定性的已传记录回溯。

### 2. Chat 模式批量下载“黑盒 ZIP”与用户认知断层
- **现状**：在 Chat 模式中，当移动端或浏览器勾选多个附件进行多选批量下载时，服务端通过动态流式 ZIP 引擎（虚拟索引 `-1`）将文件即时归档为一个 `.zip` 包下发。
- **痛点**：下载完成后，终端用户只看到一个抽象的压缩包名称（如 `eqt-chat-files-20260909-xxxx.zip`），在聊天界面中没有任何明确提示告知“这个 ZIP 里究竟打包了哪些文件”。用户无法直观校验本次下载是否漏掉了某个重要附件，也无法直接从压缩包名反查原聊天消息的对应关系。
- **第一性原理剖析**：聚合传输（Bundling）降低了传输次数，但隐蔽了数据颗粒度。系统必须在聚合传输完成后，将聚合体内部的成员清单（Manifest）投影回消息流，达成**“传输过程高聚合，信息呈现高透明”**。

## 二、 Receive 连续追加传输与会话历史架构设计

### 1. 会话生命周期与状态机重塑
在现有的 `pkg/server/server.go` 中，Receive 模式一旦所有声明文件传输完毕（`isAllActiveClientsFinished` 为真），若开启了 `--auto-stop`，系统将直接触发 `stopChannel <- struct{}{}` 关闭服务。

为了支持连续追加传输，状态机引入 **Batch（批次）与 Session（会话）的双层解耦模型**：

```
                 ┌──────────────────────────────────────────────────────────┐
                 │                 Session 状态 (长生命周期)                │
                 │                 Listening / Established                  │
                 └────────────────────────────┬─────────────────────────────┘
                                              │
                    ┌─────────────────────────┴─────────────────────────┐
                    ▼                                                   ▼
       ┌─────────────────────────┐                         ┌─────────────────────────┐
       │   Batch N: Transferring │                         │   Batch N: Completed    │
       │   (FilesDeclared > 0)   │ ──────传输全部完成────► │   (停留在完成界面)      │
       └─────────────────────────┘                         └────────────┬────────────┘
                    ▲                                                   │
                    │         点击【继续传输 (Transfer More)】          │
                    └───────────────────────────────────────────────────┘
                              (重置 Batch 状态，保留 Session 上下文)
```

#### 关键状态变迁契约：
1. **Batch 级重置，而非 Session 销毁**：
   - 移动端点击“继续传输”时，前端向服务端发送批次续订指令，或前端本地原子重置上传控制器状态；
   - 服务端维持当前的接收目录、临时凭据与网络会话，分配自增的 `batch_id`（如 `batch-001`, `batch-002`）。
2. **`--auto-stop` 保护性延迟与协同门禁**：
   - 当用户开启了自动停止参数时，单个 Batch 传输完成不再立即无条件停机，而是进入 **“优雅等待确认窗口 (Grace Period)”**（默认 30~60 秒倒计时）；
   - 在该窗口内，界面展示动态倒计时：“传输完成。会话将在 45s 后自动关闭，或点击【继续传输】保持连接”；
   - 若用户在倒计时内点击【继续传输】，前端即时向服务端发送 `POST /receive/heartbeat` 或 `POST /receive/keepalive`，重置并挂起关闭定时器；
   - 若用户无操作直至倒计时归零，安全关闭服务器。

### 3. 客户端会话历史记录 (Session History) 存储架构
- **持久层定位**：采用 `sessionStorage` 结合内存 State，确保在单次浏览器标签页开启期间持久留存，页面意外微刷新不丢记录，但在用户关闭浏览器标签页时自动清理，遵循数据最小化与隐私安全原则。
- **数据结构定义 (TypeScript / JS)**：
  ```javascript
  interface ReceiveTransferItem {
    id: string;             // 唯一文件标识
    batchId: number;        // 所属批次编号 (1, 2, ...)
    name: string;           // 文件名
    size: number;           // 字节大小
    type: string;           // MIME 类型
    uploadedAt: number;     // 上传完成时间戳 (Unix ms)
    status: 'success' | 'failed' | 'cancelled';
    storagePath?: string;   // 相对归档路径 (可选)
  }

  interface ReceiveSessionRecord {
    sessionId: string;
    startedAt: number;
    totalFiles: number;
    totalBytes: number;
    batches: {
      batchId: number;
      timestamp: number;
      items: ReceiveTransferItem[];
    }[];
  }
  ```

### 4. 服务端目录隔离与归档协同
当结合《Receive 模式移动端设备重命名与目录同步设计》时：
- 服务端可在接收目录下按批次或按设备组织落盘：
  - 默认模式：直接平铺落盘至指定接收目录（若有同名文件自动触发 `(1)`, `(2)` 递增防覆盖机制）；
  - 高级/结构化模式：按 `uploads/<device_name>/batch_<YYYYMMDD_HHMMSS>/...` 组织，保持批次物理边界清晰。

## 三、 Chat 模式多选打包透明度 (ZIP Manifest Tracking)

### 1. 动态流式打包与虚拟索引机制现状
在当前 EQT Chat 架构中（`pkg/server/chat.go`）：
- 单文件下载映射到具体的物理消息附件索引（`0..N`）；
- 多选下载时，客户端请求虚拟归档索引 `-1`（`downloadIndex == -1` 或 `archive=true`），服务端即时拉起 `zip.Writer`，通过管道并发将多个选中的附件流式压缩下发，实现内存零落地流式下载。
- 当前缺陷：一旦 HTTP 请求开始下发，聊天室消息流中没有该操作的元数据镜像，其他端（或本地刷新后）无法知道刚才打包了哪些具体消息。

### 2. 打包清单追溯架构 (ZIP Manifest Pipeline)

```
[前端多选勾选] ──► [发送打包请求 /chat/download?items=msg-1,msg-4,msg-7]
                               │
                               ▼
            ┌──────────────────────────────────────┐
            │   服务端 Chat 控制器 (chat.go)       │
            │   1. 解析目标附件列表                │
            │   2. 生成全局唯一归档包名            │
            │      eqt-chat-bundle-0909-1420.zip   │
            │   3. 构建 ZipArchiveManifest 元数据  │
            └──────────────────┬───────────────────┘
                               │
            ┌──────────────────┴───────────────────┐
            ▼                                      ▼
   【二进制通道】                          【元数据与消息总线通道】
   Range/流式 zip.Writer                  广播结构化系统消息 (System Message)
   Content-Disposition: attachment        Type: "system_zip_manifest"
   直接送达浏览器原生下载管理器           推送至双方聊天界面
```

#### 交互细节保障：
- **定位原消息 (Scroll to Original Message)**：点击条目右侧的“定位原消息”按钮，页面平滑滚动至对应的聊天气泡，并触发高亮微动画（0.8s 黄色/淡蓝微光闪烁），帮助用户在超长聊天记录中迅速建立数据索引；
- **防重复灌水**：同一批附件若被重复触发下载，通过前端防抖与归档缓存 ID 识别，只在首次下载或显式重新下载时追加系统卡片，避免刷屏；
- **样式适配**：支持浅色/深色主题，采用自适应卡片样式，在窄屏移动端上文件名过长时自动采用中段截断或自然折行（`break-word`），绝不溢出容器。

## 四、 后端通信与 API 契约设计

### 1. Receive 续传控制端点
- **`POST /receive/continue`**
  - **请求参数**：`{"session_id": "xxx", "current_batch": 1}`
  - **响应结果**：`{"status": "ready", "next_batch": 2, "server_time": 1788880000}`
  - **后端行为**：重置本次 Batch 上传计数器，重置 `--auto-stop` 计时器，向当前所有长轮询/SSE 广播就绪状态。

### 2. Chat 打包下载元数据广播
- **WebSocket 消息体**：
  - 发送方或服务端触发下载时，向房间内所有客户端同步 `EVENT_CHAT_ZIP_MANIFEST` 事件，各端无缝将清单写入聊天渲染总线。

## 五、 商业化分级规划 (Free vs Plus/Pro Tier)

根据产品长期演进战略，对批量归档与会话历史进行商业化阶梯划分：

| 功能特性 | Community 社区免费版 | Pro / Plus 商业版 |
| :--- | :--- | :--- |
| **Receive 连续追加传输** | 支持连续多轮传输，单会话最多保留最近 2 个批次历史 | **无限制多轮追加传输**，全量批次历史留存 |
| **会话历史持久化** | 内存与临时 Session 存储（关闭标签页即销毁） | **本地 IndexedDB / SQLite 持久化**，跨天历史归档导出 |
| **Chat ZIP 打包透明度** | 支持卡片展示包含文件清单与定位原消息 | **支持清单导出 (CSV/Markdown)**，支持直接在卡片内一键重新单解压 |
| **批量导出审计日志** | 基础显示 | **专业级合规传输清单与数字签名校验** |

## 六、 实施与测试验证矩阵

1. **测试断言 1 (Receive 连续传输不变量)**：
   - 验证在一个活跃会话下，完成 Batch 1（上传 2 个文件）后调用继续传输，再发起 Batch 2（上传 1 个文件），服务端接收目录正确保存 3 个物理文件；
   - 验证 `--auto-stop` 开启时，在倒计时窗口内点击“继续传输”能够成功续命，不会误杀服务。
2. **测试断言 2 (Chat ZIP 清单一致性)**：
   - 勾选 3 个不同大小的文件打包下载，验证下载到的实际 ZIP 包内部解压文件哈希与系统消息卡片内列出的成员文件名、大小 100% 吻合；
   - 验证点击卡片内的“定位原消息”能够准确命中对应 DOM 节点。
