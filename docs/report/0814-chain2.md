购买 → 铸码 → 兑换 → 解绑(吊销) 链路问题清单

我派了三个 Explore agent 分别梳理了 DRM 后端(cloudflare/eqt-drm-api)、Go 绑定层(pkg/server/license.go + desktop/gui)、GUI 前端(desktop/gui/frontend/src)，并逐个核验了关键代码与文档契约（docs/payment/*）。结论如下。

链路实现一句话

GUI 兑换走 confirmRedeem → App.ActivateLicense → POST /api/v1/activate；解绑分两层——GUI「重置」纯删本地 .lic 无网络调用，服务端解绑/吊销靠 /api/v1/verify 返回 403/404 时 ResetLicense() 降级，真正的自助解绑/退款/取消订阅/发票都在浏览器 Portal（/api/v1/user/*）里。

P1 — 建议优先处理

① 兑换码「固定时长」被在线对账滚动续期架空（后端，直接影响 GUI 兑换结果）

- cloudflare/eqt-drm-api/src/routes/drm.ts:46-56 的 evaluateLicenseExpiration 对 promo / 带 duration_days 的 admin 码，每次调用都把 effectiveExpiresAt 重算为 now + duration_days。
- activate 首次激活发的是「激活时刻+时长」的证书（符合设计）；但 verify（在线对账，drm.ts:754-797）每次也按 now + duration_days 重新签发证书 → 到期日不断后滚。
- 结果：duration_days（授权使用时长）形同虚设，真实上限只剩兑换截止日 expires_at(redeem-by)；多设备码各设备到期时间还会分叉。
- 与文档契约冲突：docs/payment/licensing-double-expiration.md §1.2 明确「用户成功激活那一刻起算固定时长」。
- 影响：运营发的「30 天使用」promo，只要 把权益拖满整个兑换窗口，属超额授权。
- 建议：首次激活时把到期时间固化持久化（写回 licenses 或 activations），activate/verify 复用同一固化值，不再每次从 now 起算。

P2 — 一致性 / 健壮性

④ Portal 认证死路由引用不存在的表（后端）

portal.ts:97-220 的 /api/v1/user/send-code / /api/v1/user/verify-code 被 index.ts:79-81 路由，但引用 auth_codes 表（全仓无任何 CREATE） 和 ushema.sql:76-80 无此列）。真实 portal.html 走 /api/v1/auth/*（可用的 canonical 路径），这两条是死路由，一旦误调即 500。建议删除死分支或改为复用 verification_codes。

⑤ Portal 管理列表不展示自然过期 / 退款态显示失真（后端 + Portal UI，管理激活码页面）

- portal.ts:223-304 /user/licenses 直接透传 DB status；自然过期（年付到期、promo 用完时长）后 status 仍为 active，portal.html:1134-1136 渲染「生效中/Active」+ 过期日期，信息失真。
- status_refunded i18n key 从未被使用（退款后 status=revoked，显示「授权终止」而非「已退款解约」）。
- 建议：/user/licenses 返回派生显示状态（is_naturally_expired / refunded），前端据此渲染。

⑥ activate 以 device_id 兜底、verify 只

activate 已激活判定含 device_id 相等（drm.ts:451），而 verify 只做 3 选 2 指纹比对（drm.ts:777-786）。实测影响有限evice-registry.ts:90-107，指纹变则 ID变），但口径不一在 device_id 碰撞/伪造场景会出现「激活成功、下次对账即被降级」。建议统一两端判定。

- 购买→铸码：paddle.ts 履约对 purchase 码 duration_days=NULL（paddle.ts:337,398），LIFETIME 用 "LIFETIME"、年付用绝对到期；idx_licenses_paddle_txn 唯一索引保证同一交易幂等。

- 吊销闭环：refund/chargeback/subscription/admin 吊销 → verify 403 → ResetLicense 降级，链路自洽；revokeLicenseSql 用 COALESCE 幂等。
