遗留/新引入的问题(均为低危,可后续排期)

1. ensureActivationDeviceIndex 对存量重复数据无预检

auth.ts 的 ensureActivationDeviceIndex 直接 CREATE UNIQUE INDEX,失败只 console.error。若 D1 里已存在重复的 (license_code, device_id) 行(来自 f07bf8a 短暂回归期),索引会静默创建失败,去重保护静默缺失。对比 ensureLicensePaddleTxnIndex 会先预检重复并 WARN 跳过。建议对齐:建索引前 SELECT license_code, device_id, COUNT(*) GROUP BY ... HAVING COUNT(*)>1 预检,有重复则告警而非静默。窗口很小(两提交同日),但生产 D1 值得确认。

2. 解绑配额仍是 TOCTOU

drm.ts:935-947 的 SELECT COUNT(unbind_records) 与后面的 env.DB.batch(DELETE+INSERT) 是两步,不在同一事务里。并发两笔解绑可同时通过 COUNT 检查,把 MAX_YEARLY_UNBINDS 突破 +1。DELETE/INSERT 的一致性已由 batch 保证,但配额本身仍非原子。影响很小(需并发且仅 +1),可接受,但严格来说 M9 只修了一半。

3. syncInFlightMu 是「阻塞串行」而非「去重跳过」

license.go:413-415 用 sync.Mutex.Lock() 阻塞等待。若后台强制对账(10s HTTP)正持锁,GUI 手动刷新(ForceOnlineLicenseSync)会阻塞排队最多 10s。它避免了并发写损坏,但没缓解、反而略加重了 M8「Wails 同步阻塞网络」的症状(M8 本身仍未修)。若想彻底解耦,应改成 try-lock + 返回「已在同步中」而非阻塞。

4. 新逻辑缺测试断言

幂等表、解绑配额、唯一索引、空 Origin 的 Sec-Fetch-Site/Referer 分支均无专门测试。本次只给离线测试的 D1 mock 补了 batch() 方法防崩溃(且该 mock 的 batch 不模拟原子回滚),没有断言新行为。建议至少补:① 空 Origin + Sec-Fetch-Site: cross-site → 403 的用例;② 重放原始 txn 命中断言「already processed」的用例。
