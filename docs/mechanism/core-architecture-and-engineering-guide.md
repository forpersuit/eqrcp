## 第一部分：第一性原理工程哲学与设计原则

在 EQT 的设计与演进中，系统的高性能与稳定性绝非来自“功能代码的不断堆砌”，而是源于对**第一性原理（First Principles）**的坚决贯彻。

### 1. 核心架构设计法则
1. **物理真实源优先，严禁基于巧合猜想**：
   - 系统的状态（如传输中、完成、百分比）必须由**底层的真实物理传输动作（Bytes Transferred、HTTP 状态码、协议 ACK）**驱动，严禁通过“对 Map 元素个数的巧合猜测（如 `len(progress) == 1`）”来推导业务状态；
2. **非阻塞异步外部调用与内存缓存隔离**：
   - 高频轮询接口（如 `/status`）必须在**微秒级（Microseconds）**内返回内存快照，严禁在主交互链路中进行同步磁盘 I/O 或外部网络 HTTP 调用；
   - 所有外部网络拉取、证书核验等高耗时操作一律使用 Goroutine 异步完成并写回内存缓存；
3. **单向数据流与读写视图分离（Projection Pattern）**：
   - 底层各传输通道（Send/Receive/Chat）保留细粒度轻量互斥锁，以极致性能处理吞吐；
   - 外部展现层通过只读快照（Snapshot）进行单向投影，避免将外部展示逻辑与底层物理传输锁强行耦合；
4. **防呆设计与最小特权**：
   - 设备指纹、授权凭据比对中，任何一方为空字符串（`""`）时直接判定跳过，严禁视为空值匹配成功，杜绝降级漏洞。

## 第二部分：本工程核心关键技术与系统设计全景

EQT 作为一款跨平台局域网自组织传输与即时通讯系统，深度融合了以下多项关键技术与架构设计：

└────────────────────────────────────────┬──────────────────────────────────────────┘
                                         │
                 ┌───────────────────────┴───────────────────────┐
                 ▼                                               ▼
┌─────────────────────────────────┐             ┌─────────────────────────────────┐
│     EQT Core HTTP/HTTPS 服务     │             │     本地 DRM 离线验证与安全子系统 │
│  • P2P 局域网自组织与短链握手    │             │  • 硬件三指纹提取与匹配防呆      │
│  • 双通道 ZIP 动态打包与单项隔离 │             │  • 离线非对称密码签名校验        │
│  • Tus 分块断点续传与回退管线    │             │  • LAN-TLS 环回通配符证书       │

│                             跨端移动浏览器 / 终端设备 H5                            │

└───────────────────────────────────────────────────────────────────────────────────┘

### 1. 局域网自组织点对点通信（Zero-Config LAN P2P）
- **核心机制**：
  - 基于 Go 标准库实现高性能轻量级 HTTP/HTTPS 服务器；
  - 启动时自动枚举宿主机活动网卡，智能推导并绑定局域网广播 IP（排除虚拟网卡与 Docker 接口）；
  - 生成随机会话密钥与唯一路由路径（如 `/receive?path=...` 或 `/chat-v2/...`），结合终端/桌面渲染的高清晰度动态二维码，移动端只需“扫码即连”，零配置实现对等内网高速传输。

### 2. 双通道传输隔离与打包伺服引擎（Dual-Channel Archive Engine）
- **核心机制**：
  - **单文件通道（`0..N`）**：针对分散小文件或单独点选文件，直接映射底层物理文件流，支持多设备按项独立记账；
  - **整包 ZIP 虚拟通道（`-1`）**：当用户选择打包下载整个目录或多文件时，服务端采用预生成临时归档文件 + HTTP Range 分片并发与进度挂接伺服；
  - **通道隔离律**：ZIP 写入进度写入虚拟索引 `-1`，严禁污染 `0..N` 物理索引，避免“小文件被 ZIP 流提前填满引发假完成”的严重缺陷。

### 3. Tus 开放分块断点续传与 Multipart 流式回退
- **核心机制**：
  - **主干通道（Tus Protocol）**：遵循 open-source Tus 规范，大文件切片为 Chunk 传输，支持 `Upload-Offset` 校验、抗移动端息屏弱网抖动，断点后自适应续传；
  - **降级通道（Multipart Streaming）**：针对旧版浏览器或受限网络环境，提供标准的 `multipart/form-data` 流式回退机制；
  - **完成门禁（Completion Gating）**：客户端通过 `?done=true` 显式信号汇聚，结合 `isAllActiveClientsFinished()` 统一评估退出时机。

### 4. HTTP RFC 7233 / RFC 9110 Range 规范与客户端协商
- **核心机制**：
  - 严格支持 `Range: bytes=start-end` 请求头，返回 `206 Partial Content` 与 `Content-Range`；
  - 深度兼容 iOS Safari 及各类移动播放器的流媒体探测（如首请求探查 `bytes=0-1` 元数据，随后按需 Seek 读取 moov box）；
  - 在免额超限限速场景下，采用自研的带速率限制的 `io.ReadSeeker` 封装，托管给标准库 `http.ServeContent`，杜绝直接以 `200 OK` 破坏 RFC 规范导致的播放器崩溃。

### 5. Wails 桌面端混合架构与反应式状态投影
- **核心机制**：
  - 前端采用 Svelte 构建极致轻量的响应式交互界面，后端基于 Go 实现底层操作系统系统级调用；
  - **非阻塞内存投影**：桌面端 Agent 通过 `statusHook` 监听核心服务的 `TransferStatusSnapshot`，微秒级捕获传输状态、总已完成字节数、活跃设备数（各活跃客户端的实时速率经 `ClientStates[].Speed` 暴露）；
  - 主线程绝对禁止发起同步阻塞式 I/O，页面渲染函数遵循纯函数映射（`Data -> DOM`），避免内存泄露与数据漂移。

### 6. 离线密码学硬件指纹授权与本地验证体系 (DRM)
- **核心机制**：
  - **多维硬件指纹提取**：自动采集主板 UUID、CPU 序列号、物理磁盘序列号并执行 SHA-256 离线单向哈希；
  - **防呆比对规则**：指纹比对时任何单项为空字符串（`""`）直接忽略跳过，必须保证至少 2 项有效非空特征完全吻合；
  - **Ed25519 / 椭圆曲线离线数字签名**：许可证以加密字节块存储，软件纯离线即可使用内嵌公钥验证签名的合法性、到期日与功能 Tier，配合 Cloudflare D1 Serverless 数据库进行边缘在线鉴权与激活重置。

### 7. LAN-TLS 环回自签名与 DNS-01 通配符证书支持
- **核心机制**：
  - 现代移动浏览器对剪贴板访问（Clipboard API）、摄像头拍照、PWA 离线存储均强制要求 **Secure Context (HTTPS)**；
  - EQT 深度集成了 LAN-TLS 环回体系：具备局域网 DNS-01 挑战应答基础设施与证书加载管线，配合外部 ACME 自动化客户端完成通配符证书签发与加载，并在无法连接外网时平滑降级到内存动态自签名证书，确保局域网内所有终端享有原生 HTTPS 体验。

## 第三部分：工程质量与测试理论指导（测试第一性原理）

本次 `autoStop` 在 Receive 模式下失效事件，暴露出我们过去自动化测试思维中的重大盲区。本节明确本工程的**自动化测试理论指导体系**。

### 1. 深度批判：测试反模式与防线断层（Anti-Patterns）

#### ❌ 反模式 1：单测镜像复刻与层级断层（Mirror Testing & Layer Boundary Disconnect）
- **表现**：测试用例未调用系统真实公开入口，而是在单测内部手动复制代码分支或仅单测内部纯逻辑算法，缺少外层联动。
- **边界界定与危害**：
  - 针对 `isAllActiveClientsFinished()` 这类核心收敛算法内部逻辑的单元测试是**合理且必需的**；
  - 但**算法测试不能替代外层状态机契约测试**：若缺乏从最外层 HTTP Handler（如 Tus 收到 `?done=true`）驱动全局生命周期联动的集成用例，一旦外层 Handler 内部出现直接将全局状态置为 `"completed"` 的违规改动，内部算法单测依然全绿，从而产生“测试全通但真实功能失效”的防御真空。

#### ❌ 反模式 2：黑盒盲区与路径失衡（Asymmetric Coverage）
- **表现**：重点测试路径（如 Send 模式）写了数十个用例，而新演进路径（如 Receive Tus）只测了底层的流写入，漏掉了最关键的状态流转和收敛门禁。
- **危害**：边缘改动击穿全局生命周期。

#### ❌ 反模式 3：跨层 Mock 盲信（Mock Over-confidence）
- **表现**：Server 层测 Server 的，GUI Agent 层拿假数据喂给 Agent，双方都 100% Pass，但两层拼接在一起时，Server 广播的一个微小状态变化直接导致 Agent 误退。

### 2. 核心测试理论：黑盒状态机不变量契约测试（Invariant Contract Testing）

为了彻底杜绝此类问题，工程必须全面落地**不变量契约测试**：

```
                ┌──────────────────────────────────────┐
                │          测试用例 (Test Runner)       │
                └──────────────────┬───────────────────┘
                                   │
               发起真实 HTTP 请求   │ (POST /receive?done=true)
               或标准公开 API 调用  │
                                   ▼
        ┌──────────────────────────────────────────────────────┐
        │                 真实 Server 实例 (Mux)               │
        │                                                      │
        │   • 真实路由分发 (ServeHTTP)                         │
        │   • 真实状态机变迁 (updateStatus / recordStatus)      │
        │   • 真实生命周期信道 (stopChannel)                   │
        └──────────────────────────┬───────────────────────────┘
                                   │
                                   ▼
                ┌──────────────────────────────────────┐
                │        核心系统不变量断言检查         │
                │                                      │
                │  • 不变量 A：KeepAlive 状态绝不退化   │
                │  • 不变量 B：AutoStop 依门禁优雅停机  │
                │  • 不变量 C：字节与百分比严格单调非负 │
                └──────────────────────────────────────┘
```

#### 原则一：测试必须打在系统公开入口
- **单测不准调用内部未导出的细粒度逻辑函数来模拟流程**；
- 必须通过 `srv.mux.ServeHTTP(recorder, request)` 或导出的顶层 API（如 `srv.SetAutoStop(bool)`）驱动；
  *(注：`srv.mux` 为 `package server` 内部未导出字段，仅限于服务模块内部 `*_test.go` 契约单测中直接调用；跨模块如 GUI Agent 测试应通过顶层导出 API 或 HTTP 客户端测试夹具驱动)*；
- **输入是真实的 HTTP 报文，系统才能经历真实的上下文检查、锁竞争与状态流转**。

#### 原则二：断言必须落在全局不变量（System Invariants）
无论系统代码如何重构、无论新增了什么协议，系统的**生命周期不变量**必须被刚性断言保护：

1. **不变量 A（长连接防退 - KeepAlive Protection Invariant）**：
   $$\forall t, (\text{KeepAlive} = \text{true} \land \text{autoStop} = \text{false}) \implies \text{State} \neq \text{"completed"} \land \text{State} \neq \text{"stopped"}$$
   *解读*：只要长连接开启且未激活自动停止，任何客户端传完、任何报错、任何子任务结束，全局状态绝对禁止自发变迁为终结态，`stopChannel` 绝对禁止触发。

2. **不变量 B（按需收敛 - AutoStop Gating Invariant）**：
   $$\text{TriggerStop} \iff (\text{autoStop} = \text{true} \land \text{isAllActiveClientsFinished}() = \text{true}) \lor \text{UserExplicitStop}$$
   *解读*：只有当所有活跃客户端确已完成、且自动停止开启时，服务才被允许向全局广播 `completed` 并向桌面端发送退场信号。

3. **不变量 C（数据单调递增 - Progress Monotonicity Invariant）**：
   $$\text{BytesDone}(t_2) \ge \text{BytesDone}(t_1) \quad (\forall t_2 > t_1)$$
   *解读*：任何活跃传输中的单项与总体进度，已传输字节数在时间轴上必须严格单调递增，绝不允许因轮询波动而出现瞬时回退。

## 第四部分：开发者自检与交付 Checklist

在每一次向本项目提交代码前，请严格对照以下清单自检：

- [ ] **改动最小化**：是否严格遵循 Surgical Changes，仅修改与目标直接相关的代码？
- [ ] **消除猜想式判定**：是否在状态计算中引入了任何依赖 Map 尺寸、字符串包含的非物理判据？
- [ ] **非阻塞承诺**：在 `/status` 及轮询链路中，是否保证零阻塞网络调用与零磁盘 I/O？
- [ ] **真实入口驱动测试**：是否为新改动编写了基于 `ServeHTTP` 的端到端状态机契约单测？
- [ ] **不变量验证**：运行全量回归 `go test ./pkg/server ./cmd`，验证系统四大生命周期不变量未受破坏；
- [ ] **版本号递增**：若引入了任何可见功能或体验优化，是否已按规范将小版本号递增（`pkg/version/version.go` 与 `wails.json`）。
