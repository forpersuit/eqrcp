# HTTPS 绿锁与证书常见疑问

在使用手机浏览器扫描 EQT 生成的二维码时，部分用户会对地址栏中显示的“安全绿锁 🔒”或偶发的“证书警告”感到好奇。本文为您全面解答底层密码学原理与排查方法。

---

## 为什么局域网传输必须使用 HTTPS？

传统的局域网互传工具普遍采用纯明文 `http://`。但这种做法在现代操作系统与浏览器规范下面临无法逾越的技术死穴：

### 1. iOS Safari 内存崩溃（1.5GB OOM Trap）
苹果 iOS 系统的 WebKit 内核在未加密的 `http://` 页面下，出于沙箱安全策略限制，会切断内核级的直接落盘通道，转而将数据全部灌入浏览器运行内存缓存中。实测在明文 HTTP 下传输超过 1.5GB ~ 2GB 的高清视频时，Safari 标签页会因内存耗尽（OOM）而强行闪退崩溃。**只有在 HTTPS 安全通道下，WebKit 才会开放完整的流式直写能力**。

### 2. 现代 Web 前沿安全权限收紧
W3C 规范已全面收紧现代 Web API 权限。自动剪贴板同步、系统原生分享面板（Web Share API）、Web Crypto 加密硬件加速等高级功能，**强制要求运行在 HTTPS 安全上下文中**。明文 HTTP 会直接被浏览器剥离这些能力。

### 3. 公共 Wi-Fi 下的安全隐患
在公共咖啡馆、酒店或开放办公区，任何攻击者通过基础抓包工具均可轻而易举捕获明文 HTTP 传输的照片和聊天内容。

## 为什么 EQT 的局域网直连能获得公信绿锁？

很多用户好奇：“**既然数据是在局域网直连，为什么浏览器地址栏会有正规的公信安全锁？**”

1. **Let's Encrypt 专属通配符证书**：
   电脑端首次启动时，在本地生成唯一的专属 ECDSA P-256 私钥，并通过 Cloudflare 协调器向全球公信证书机构 **Let's Encrypt** 完成 DNS-01 自动化校验，签发该设备专属的通配符证书（`*.<NodeID>.direct.eqt.net.im`）。该通道已获官方高额签发配额支持（每周 20,000+ 张），并配备 Multi-CA 智能容灾机制，保障大规模设备全天候稳定置备。
2. **纯数学无状态回环 DNS（eqt-dns）**：
   手机扫码访问 `https://192-168-1-50.<NodeID>.direct.eqt.net.im:8080/` 时，权威 DNS 服务器以纯内存数学解算将该域名的 IP 部分直接解析为局域网地址 `192.168.1.50`。
3. **权威根证书认证 + 局域网物理交换**：
   手机浏览器对域名进行公信 TLS 校验（通过内置的 Let's Encrypt 根证书验证通过，呈现绿锁），而实际的 TCP 数据包则 100% 走本地 Wi-Fi 路由器物理传输，**不经过任何外部服务器**。

## 常见现象与排查指南

### 现象 1：地址栏正常显示安全锁 🔒
这是 EQT 的标准运行状态。证书有效期为 90 天，EQT 客户端在启动和空闲时会自动检查并于临近到期时静默续签，用户无需任何手动干预。

### 现象 2：手机提示“此连接不是私密连接 / 证书无效”
通常有以下两种诱因：
- **诱因 A：电脑首次安装启动时完全处于无网状态**
  若电脑首次启动 EQT 时处于纯离线环境，软件无法与 Let's Encrypt 通信置备证书，会自适应启用本地临时证书保障物理可用性。
  *解决办法*：将电脑连接一次外网，重启 EQT 等待数秒完成初始证书自动置备即可。
- **诱因 B：局域网 DNS 劫持或使用了阻断公网解析的内网 DNS**
  *解决办法*：在无公网 DNS 解析能力的封闭局域网中，可直接在浏览器警告页点击“高级” ➔ “继续前往（不安全）”，纯局域网的数据传输功能依旧完整可用。
